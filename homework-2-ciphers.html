Homework 2: Encryption and cryptanalysis

Encrypt the same message in two ways, then investigate what makes each key recoverable.

From the previous exercise to encryption

The earlier pages introduced Q = dG and the role of secp256k1 in Ethereum. The interactive curve there was a smaller illustration, y² = x³ + 7 (mod 17); it did not define a message-encryption protocol. Here we keep the same point-addition idea, use the actual secp256k1 curve, and explicitly define a toy hybrid encryption scheme.

Both schemes below encrypt “Meet me at the library at noon.” You can change the message and keys. The ECC recipient key is deliberately restricted to 1 ≤ d ≤ 4096, only 12 bits of choice. This makes the attack practical even though the underlying curve is large.

Curve parameters and implementation

The equation is y² = x³ + 7 modulo p, where p = 2²⁵⁶ − 2³² − 977. The generator G has prime order n and the curve has cofactor 1. Coordinates below are hexadecimal, using the parameters in Standards for Efficient Cryptography 2 (SEC 2).

1. Encrypt and decrypt the same message

Run the demonstration to inspect both ciphertexts.

Caesar cipher

Number the letters A = 0, …, Z = 25. Encrypt with c = (m + s) mod 26 and decrypt with m = (c − s) mod 26. The same secret shift is used in both directions.

Only A–Z and a–z are shifted. Letter case, spaces, punctuation, numbers, and other Unicode characters remain unchanged. Thus the transformation is reversible, but those unchanged characters leak directly.

Toy secp256k1 hybrid

  1. The recipient chooses private d and publishes Q = dG.
  2. The sender draws fresh random r ∈ {1,…,n−1}, computes R = rG and shared point S = rQ.
  3. HKDF-SHA-256 derives an AES-256 key from S. AES-GCM encrypts the UTF-8 message with a fresh 96-bit nonce and adds a 128-bit authentication tag.
  4. Send (R, nonce, ciphertext, tag). The recipient computes S = dR = drG = rQ, derives the same key, verifies the tag, and decrypts.

This is an educational construction, not a claim of compatibility with a standard ECIES profile. The BigInt curve code is not constant-time or production-audited. SHA-256, HKDF, and AES-GCM use the browser's Web Crypto API; use HTTPS or localhost if encryption is unavailable.

Both methods use a key-dependent reversible procedure. Their attack surfaces differ: Caesar exposes language structure, whereas this ECC example is broken by the tiny set of possible recipient keys, regardless of what the message says.

Why Caesar preserves its statistical signature

If fⱼ is the observed plaintext fraction for letter j, encryption merely permutes the fractions. Therefore H = −Σ fⱼ log₂ fⱼ and IC = Σ cⱼ(cⱼ − 1) / [L(L − 1)] remain the same (IC needs L ≥ 2). These are descriptive letter statistics, not the uncertainty of the entire message or the secret key. Neither statistic alone identifies the shift; matching the labelled frequencies to a language model does.

3. Recover a Caesar key from language statistics

Train on the bundled English corpus: 11,761 letters from original passages about everyday life. Keep only A–Z, fold case, and count each letter. Add-one smoothing gives pⱼ = (countⱼ + 1) / (T + 26), avoiding zero expected counts.

  1. For each candidate shift s = 0,…,25, undo the shift and count the resulting letters Oⱼ.
  2. For ciphertext length L in letters, compute expected counts Eⱼ = Lpⱼ.
  3. Score the candidate with χ²(s) = Σ (Oⱼ − Eⱼ)² / Eⱼ.
  4. Choose the shift with the smallest score, then inspect the candidate plaintext.

This uses a chi-square distance to rank candidates, not a calibrated significance test. In particular, tiny expected counts in short samples make a formal chi-square interpretation inappropriate. Ties are resolved by taking the smaller shift.

Alternative approaches and their costs

Exhaustive search produces all 26 plaintexts in O(26L) work. It guarantees the correct one is in the list; recognising it still requires language evidence, known plaintext, or human judgement. Statistical scoring automates that choice, so exhaustive search and frequency analysis are complementary.

Most frequent letter: align the most common ciphertext letter with the most common training letter (E here). This throws away the other 25 counts and is fragile on short passages. Count ties use alphabetic order in this implementation.

Bigrams: count all adjacent letter pairs after removing nonletters, including pairs across word boundaries. Use add-one smoothing over 26² = 676 pairs: p(ab) = (count(ab) + 1)/(T − 1 + 676). Minimise −Σ log p(ab) for each candidate. It captures some letter order and often helps on short texts. It is a scoring heuristic using overlapping pairs, not a calibrated probability of the whole message. With fewer than two letters all bigram scores tie.

Once the letter counts are computed, chi-square ranking needs only 26 × 26 terms, for O(L + 26²) work. Bigram scoring here scans each candidate in O(26L). Larger n-grams may capture more context but need more training text and smoothing.

Observed: at 5 letters, chi-square recovered 58 keys and bigrams recovered 76. By 50 letters both recovered every key in this run, while the one-letter heuristic recovered 59. Longer samples tend to resemble the reference distribution more closely, but success need not increase monotonically on every dataset.

Limitations: these are modest, purpose-written corpora in a similar register, not a representative benchmark of English. Sample windows can overlap, so the trials are not independent evidence and 100/100 is not a universal success guarantee. The pseudorandom generator is for repeatability, not secure key generation. Names, abbreviations, specialised vocabulary, a different language, or deliberately unusual letter distributions can defeat the ranking even in longer texts.

A ciphertext of one letter may plausibly decode to “A” or “I”; statistics cannot eliminate that ambiguity. A repeated letter or uniformly distributed random text offers little reliable English-language evidence. Preserve several candidates when the evidence is weak, and treat the score gap as a comparison, not a probability of correctness.

5. Attack the restricted ECC key space

The attacker knows G, Q, the bound 4096, and the encrypted packet. Start at P = O; repeatedly add G. At step j, P = jG. Compare both coordinates with Q. When they match, j is the recipient's private key. Decrypt using jR and the same key derivation. This search does not read the private-key input or use English letter frequencies.

There are at most 4096 candidate checks, and an average of (4096 + 1)/2 = 2048.5 for a uniformly chosen key. Each next candidate needs one point addition, rather than a fresh scalar multiplication. Matching a full public point identifies the key exactly within this range: distinct scalars below n give distinct points. The amount or language of ciphertext is irrelevant to recovering d.

Why this does not scale: a properly sampled secp256k1 private key has approximately 2²⁵⁶ possibilities. Linear enumeration is infeasible. Generic classical discrete-logarithm methods such as Pollard rho take roughly √n ≈ 2¹²⁸ group operations, rather than 2²⁵⁶. Thus a 256-bit scalar is associated with roughly 128-bit generic classical security, assuming a sound protocol and implementation.

Alternative attacks and protocol weaknesses

Baby-step giant-step uses roughly O(√B) work and memory for a range of B possible keys; Pollard kangaroo targets a known interval with expected work of that order and much less storage. At B = 4096, √B = 64; this is an order-of-growth comparison, not a promise of exactly 64 operations. They are unnecessary for this tiny demonstration but show why interval restrictions are especially dangerous.

If the sender also chose r from a tiny range, recovering r from R would reveal S = rQ even when the recipient's d was strong. This implementation deliberately samples r over the full group range. Restricting d is sufficient to break it.

Other weaknesses are separate from the private-key range: unauthenticated XOR encryption permits tampering; reusing a keystream leaks relationships between messages; reusing an AES-GCM nonce with the same key is unsafe; accepting invalid curve points can expose secrets in some protocols. Here points are checked, R and Q are bound into derivation and authentication, fresh randomness is used, and a GCM tag is verified. Nevertheless, this teaching implementation has no constant-time guarantee, sender authentication, audited protocol design, or secure key storage. Strengthening the key range alone would not certify it as production software.

Conclusion

Caesar encryption rotates the alphabet without hiding its structure. A corpus-derived model can therefore rank its 26 keys, with longer, ordinary-language samples generally providing better evidence. In the ECC hybrid, scalar multiplication lets sender and recipient derive the same encryption key in different ways; letter-frequency matching no longer applies. Yet restricting the private scalar to 4096 choices makes exact recovery easy. A large curve cannot compensate for a small secret.
