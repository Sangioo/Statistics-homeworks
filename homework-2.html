Homework 2: From mnemonic to Ethereum address

Different cryptographic tools perform different steps.

The wallet pipeline

A wallet starts with random entropy. A common Ethereum externally owned account (EOA) then follows this path:

Entropy → BIP-39 mnemonic → BIP-39 seed → BIP-32/BIP-44 private key → secp256k1 public key → Keccak-256 address → EIP-55 checksummed address

StepPurpose
BIP-39Encodes random bits as a memorable word list, with a short SHA-256 checksum. PBKDF2-HMAC-SHA512 turns the mnemonic and optional passphrase into a 512-bit seed. The mnemonic itself is not a private key.
BIP-32Uses HMAC-SHA512 to derive a master private key and chain code from the seed, then a reproducible tree of child keys.
BIP-44Defines the path layout m/purpose'/coin_type'/account'/change/index. One common path for the first Ethereum address is m/44'/60'/0'/0/0; 60 identifies Ethereum and ' marks a hardened step. Wallets may use other paths.
secp256k1Turns private scalar k into public point Q = kG. Ethereum also uses this curve with ECDSA to sign transactions. This is public-key cryptography, not hashing.
Keccak-256Hashes the 64 bytes x || y of the uncompressed public key, excluding its leading 0x04 byte. The last 20 bytes of the 32-byte digest form the Ethereum address.
EIP-55Hashes the lowercase hexadecimal address as ASCII text and uses the hash to choose upper or lower case for letters. It helps detect typing errors; the underlying 20 address bytes do not change.

Public example: the known BIP-39 mnemonic “abandon” repeated 11 times followed by “about”, with an empty passphrase and path m/44'/60'/0'/0/0, leads to 0x9858EfFD232B4033E47d90003D41EC34EcaEda94. This example is public; it must never be used to store funds. A different passphrase or derivation path changes the result.

Why several techniques?

Key generation needs new unpredictable randomness. Key derivation reproducibly computes keys from an existing seed and a path. BIP-39, BIP-32 and BIP-44 manage those secrets and paths. Public-key cryptography links a private key to a public key and permits digital signatures.

Hashing maps data to a fixed-size digest; Keccak-256 is used here to make the address. A checksum adds information for detecting errors. Encoding changes representation, such as bits to mnemonic words or address bytes to hexadecimal characters. EIP-55 adds checksum information through letter case. None of these roles replaces the others.

Statistical properties and limits

  • Good starting entropy and a correctly generated private scalar must be unpredictable. BIP-39 words include checksum bits, so their patterns are not independent random words. Derivation is deterministic: the same mnemonic, passphrase and path give the same keys.
  • Public points lie on a curve. Their x and y coordinates are related, even if private scalars are uniformly selected. On a suitable large curve, the relevant security question is whether recovering k from Q is hard.
  • Keccak-256 digests should have well-distributed bits and show an avalanche effect: a one-bit input change typically changes about half the digest bits. The address keeps only the last 160 bits. A small sample that looks balanced is not proof of hash security.
  • Nearby BIP-44 indices produce different derived keys and addresses, but they share one seed. A low visible correlation between index and address does not prove independence or secrecy.
  • EIP-55 case is derived from address hash bits. It provides error detection, not new address randomness, encryption or proof of ownership.

Historical context

YearMilestone
1977RSA public-key cryptography was described in an MIT memo.
2001–2002SHA-2, including SHA-512: draft in 2001, final FIPS 180-2 standard in 2002.
2012BIP-32 hierarchical deterministic wallets.
2013BIP-39 mnemonic and seed generation.
2014BIP-44 multi-account path convention.
2015NIST standardized SHA-3, based on Keccak.
2016EIP-55 mixed-case Ethereum addresses.

SHA-2 versus Keccak/SHA-3: SHA-512 belongs to SHA-2. Keccak is the design selected for SHA-3, but Ethereum's Keccak-256 is not the standardized SHA3-256: their padding/domain-separation conventions differ, so their outputs differ.
