HMWK 2 — From a wallet seed to an Ethereum address

A wallet normally uses a random source of entropy to create a mnemonic, then derives keys deterministically. The mnemonic is not itself the Ethereum private key.

Mnemonic → BIP-39 seed → BIP-32 / BIP-44 child private key → secp256k1 public key → Keccak-256 → 20-byte Ethereum address → EIP-55 checksum casing

Role of each standard or primitive

Technology Purpose Simple explanation
BIP-39 Mnemonic and seed generation Encodes random entropy as a list of words, adding a small SHA-256-based checksum. The words and optional passphrase are processed with PBKDF2-HMAC-SHA512 (2048 iterations) to obtain a 512-bit seed.
BIP-32 Hierarchical deterministic key derivation Derives a tree of child keys from one seed using HMAC-SHA512 and a chain code. The same seed and derivation path reproduce the same keys.
BIP-44 Path convention for multi-account wallets Organizes derived keys with the path m / purpose' / coin_type' / account' / change / address_index. A common Ethereum first-address path is m/44'/60'/0'/0/0.
secp256k1 Public-key cryptography and signatures The private key is a scalar k; the public key is Q = kG. Ethereum uses this curve with ECDSA signatures to authorize transactions.
Keccak-256 Hashing for address derivation Hash the 64-byte public-key coordinates x||y (the uncompressed public key without its leading 0x04 byte). The Ethereum address is the last 20 bytes of the 32-byte Keccak-256 digest.
EIP-55 Address checksum encoding Hashes the lowercase hexadecimal address (without 0x) with Keccak-256. The hash determines which alphabetic address characters are uppercase. This helps detect typing mistakes; it does not encrypt the address or prove ownership.

Key generation versus key derivation

Key generation begins with fresh randomness/entropy to create the initial secret material. Key derivation deterministically computes child keys from an existing seed or parent key and a path. A wallet can therefore back up one mnemonic and recreate many addresses without separately backing up each private key.

Hashing, checksums and encoding

Hashing maps input data to a fixed-size digest; it is not encryption and is not normally reversible. Checksum casing in EIP-55 gives a way to spot many address transcription errors. Encoding turns data into a representation people or software can handle: mnemonic words represent entropy, hexadecimal represents bytes, and EIP-55 changes letter case without changing the underlying 20-byte address.

Historical context (approximate order)

Year Milestone Why it matters
1977 RSA proposed at MIT (the famous RSA paper was published in 1978) Early practical public-key cryptography and digital-signature design.
2001–2002 SHA-2 family / SHA-512 standardized NIST's FIPS 180-2, which specifies SHA-256, SHA-384 and SHA-512, was published in August 2002.
2012 BIP-32 Standardized hierarchical deterministic wallets.
2013 BIP-39 Standardized mnemonic words and seed generation.
2014 BIP-44 Standardized a multi-account hierarchy and derivation-path roles.
2015 NIST SHA-3 (FIPS 202) NIST standardized SHA-3, based on its selected Keccak design.
2016 EIP-55 Specified mixed-case checksum encoding for Ethereum addresses.

SHA-2 versus Keccak/SHA-3: these are different hash-function designs. SHA-512 belongs to SHA-2. NIST SHA-3 was based on the Keccak design, but Ethereum's Keccak-256 is not identical to standardized SHA3-256: the padding/domain-separation convention differs, so the outputs differ. Implementations must use Ethereum-compatible Keccak-256 for Ethereum address derivation.

Why not use one algorithm for everything?

These steps solve different problems. BIP-39, BIP-32 and BIP-44 make secrets easier to back up and organize into reproducible keys. secp256k1 links a private key to a public key and supports signatures. Keccak-256 compresses the public key into the short address identifier. EIP-55 adds a human-readable error check to the hexadecimal representation. One primitive cannot replace all these roles without losing required functionality.

Statistical properties in the real pipeline

For a good wallet, initial entropy should be unpredictable. BIP-39 words encode that entropy and include only a small error-detection checksum; the mnemonic is not designed to look like uniformly random text. A properly selected private scalar should be unpredictable in its valid range. For secp256k1, public points follow the curve's algebraic structure, so public-key coordinates are not arbitrary independent bits. Keccak-256 is designed to have digest outputs that look pseudorandom and to exhibit avalanche behavior: changing input bits should typically change about half the digest bits. EIP-55 letter casing reflects hash bits and is for typo detection, not secrecy. Statistical appearance alone does not prove cryptographic security.

Security reminder: never enter a real recovery phrase or private key into a homework demo or an unfamiliar website. This page does not derive real wallet keys and does not connect to a blockchain.
